# 浏览器对抗验收协议

## 调度
协调者先记录目标 revision + working diff 身份、测试 origin、运行 ID、角色账号、种子数据、输出目录和预算。按实际改动选择角色，默认 1 名独立 reviewer，多风险 2–3 名，并行上限建议从 3 开始。并行是探索效率策略，不是负载测试。

## 两种模式
1. 固定回归：Playwright Test 驱动已批准流程，复用真实服务，关键状态用断言检验。
2. 首次体验：给 Agent 身份、入口 URL、目标、账号与允许操作边界，首轮不提供源码、页面路由、选择器或开发者操作手册。失败后再由源码 reviewer 定位。

## 角色任务
- 陌生选手：从公开首页了解如何找到伙伴，找到合适资料并发起联系/申请；记录入口是否可发现、文案是否清楚。
- 队长：上传合成材料，正式提交，找回回执；探查断网、失败、重复、过期登录、截止边界。
- 非技术主办方：查到指定队伍的有效记录、导出核对、发现异常时知道如何接管。
- 评委：仅在评审功能改动时加入，检查草稿、确认、修改与汇总语义，沿用已定规则。
- 横向 UI/UX：按需检查状态透明、取消与恢复、手机、键盘及字体，避免和其它角色重复所有流程。

## 隔离
每个 Agent 使用唯一 `run_id + role` 的命名浏览器 session、独立账号与独立数据命名空间。共用后端时，独立 cookie 不会隔离队伍、提交记录和活动时间。双人互动场景显式共享某个测试队伍并设同步点；其他案例不能抢写它。用测试专属 origin、数据库、OSS bucket/prefix 和邮件/通知替身，禁用真实短信、邮件和收费调用。

不复用个人浏览器 profile。测试前明确 origin allowlist、可写资源、清理清单、每 Agent 步数/时间/token 上限。清理仅删除本轮拥有的数据，不执行无条件全库清空。浏览器、MCP、CDP 和报告服务只监听本地或受控网络，不公开调试端口。

## 权限是真约束
“只读 reviewer”是职责，不自动提供文件系统只读。当前 Codex 子 Agent 继承父会话权限，agent TOML 里的 sandbox_mode 不能覆盖父会话。实际隔离需受限工具、OS/容器权限或独立浏览器审查运行环境；不支持时明确降低了独立性保障，不能声称已强隔离。

## 故障矩阵
- UI 确定性：延迟响应、500、401/过期会话、断网、重复点击、多标签页、刷新/返回、无数据、长名称。
- 流量语义：延迟返回不是限速上传；用可控服务端流或受控代理验证真实字节/速度变化。第一期可先验证可见 pending 和错误恢复，再补带宽实测。
- 时间：服务端业务时间和时区为准；浏览器 Clock 不会改变 Django/数据库的截止判断，需隔离数据或服务端测试时钟。
- AI/外部服务：可使用受控 Mock 验证等待与失败状态，再独立跑小规模真实集成验证。两类结果分别记录。
- 网络恢复：客户端响应丢失后先查询操作状态，不能把重试按钮当作幂等性的证明。

## 证据与退出
每个完整动作捕获：用户意图、前状态、操作、可见反馈、后状态、断言、截图；关键步骤保存 trace 和请求关联 ID。隐藏 Cookie、Authorization、私人信息、真实材料与 OSS 签名 URL。

审查者不改应用源码、测试断言、基线或契约。修复由原任务授权的实现 Agent 做，修复后原审查路径复测。自修复最多两轮建议值，超过则报告阻塞，不能通过减少检查“完成”。工具不可用、缺账号或环境失败记录 blocked，保留日志和可执行下一步。

问题进入既有 adversarial-audit ledger，沿用稳定 ID；纯偏好标注为建议。已有相同根因则附新证据，不堆叠重复报告。没有成立的问题是有效结果。
