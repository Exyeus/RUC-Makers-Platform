# 反复问题 → 可执行约束
借鉴 poteto 的 pstack `correct`，结合现有审计 ledger，而不是持续堆长提示词。

当用户再次指出同类问题，或同根因至少两次出现时，由 `hackathon-regression` 做一次小范围固化。严重权限/数据损坏问题第一次就应补回归；不必等待复发。

1. 从 ledger、真实 commit、失败测试和用户反馈找出证据，按根因分组。
2. 优先用架构消除错误路径：统一状态拥有者、复用上传任务与提交服务、减少手工同步。
3. 然后考虑类型/Schema 让非法状态难以构造；Django/Python 项目按现有结构实现，不强行改语言。
4. 可确定的坏写法使用 AST/lint，报错必须说明替代 API、组件或修法。历史广泛存在的问题采用增量门槛，不把所有旧代码一夜重写。
5. 用回归测试证明外部行为；对不能完全机器判断的审美/可理解性才写简短审查规则。
6. 把历史失败样本喂给新规则，必须看见失败；修正版必须通过；还要准备合理反例验证不会误伤。
7. 同一命令用于本地与 CI。记录误报和执行成本；已经由结构消除的问题可以删除重复文字规则。

建议在现有 ledger 的 finding 下记录 enforcement_path、regression_test、counterexample、owner、expires/retirement。不要另建需要同步的第二套问题数据库。

示例：反复“上传后页面不更新” → 统一 upload task 状态与订阅/轮询机制 → 端到端验证服务端确认后列表刷新 → lint 禁止新代码绕开统一路径（仅在替代路径确实可用后启用）。

示例：反复“先占位后实现” → 明确任务卡验收示例 → Stub 在关键流程的测试中失败 → 延期必须带责任人、Issue、时间及范围决定。规范约束交付真实性，不惩罚如实记录的技术债。
