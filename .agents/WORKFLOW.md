# 轻量协作：让信息跟着任务走

一张卡说明需求，一个小分支完成一件事，一个 PR 留下验证与交接信息。流程服务于交付；需求还没完全定稿时，可以先做不依赖它的工作，把待确认项写清楚。

这是当前分工，不是审批链。每张卡写清实际负责人；需要别人提供输入时，点名说明信息和时间，不默认某人一直在线。

## 需求怎么交到实现者手里

使用 [六字段任务卡](templates/task.md)：做什么、需求链接、负责人输入、正确例子、演示时间、进展 / PR。

- 每项需求只保留一张主任务卡，作为范围、状态与验收例子的单一主源；需求链接保留依据，PR 与聊天引用主卡，不维护互相竞争的副本。
- 在“进展 / PR”区分 `提案`、`已定`、`待确认`；有想法不等于已承诺实现，由卡中的需求确认者确认后再标“已定”。
- 用一句话描述谁在什么场景需要什么结果；需求链接指向最新约定，聊天中的决定也补回卡里。
- 负责人输入写实现者、确认者和所需材料；不确定项写“待谁在何时确认”，别让它藏在私聊里。
- 正确例子给出输入与预期结果，涉及权限或截止时间时再补一个不应通过的例子。
- 演示时间是约定的反馈点，可以调整；进展写下一步、阻塞和 PR 链接，避免只写“进行中”。
- 需求改变时先更新卡中的例子与范围，再同步到 PR；复杂设计只在确有分歧或风险时另开短说明。

检查卡写法示例（`提案`，基于已有上传流程；尚未运行，不代表当前版本已验证）：

| 字段 | 样例 |
| --- | --- |
| 做什么 | 核实上传访问隔离：陌生账号不能查看或续传他人的上传会话 |
| 需求链接 | `app/tests/hackathon/test_accounts_uploads.py::test_expiry_deadline_and_ownership`；先核实目标 revision 与已定需求是否一致 |
| 负责人输入 | 张泽昌拟做验证；孙谦提供入口说明；实际安排由卡中确认 |
| 正确例子 | 合成 PDF 创建上传会话；切换陌生账号访问状态 / 上传分片应被拒绝；已有测试预期为 404 |
| 演示时间 | 由本周短演示确定；定时后替换为实际日期 |
| 进展 / PR | 提案，未运行；先核对当前源码与测试，验证后补结果及 PR（若需要改动） |

## 从分支到 PR

1. 读根规范及匹配的文件规则，确认实际源目录、当前分支和未提交改动。学校默认集成分支为 `main`，从 `origin/main` 开 `feat/`、`fix/` 或 `docs/` 小分支；按 [BRANCHES.md](BRANCHES.md) 隔离上游与服务器现场。
2. 优先在 `app/eventyay/hackathon/` 和 `app/tests/hackathon/` 内完成活动功能；改到公共模块时在 PR 说明受影响入口。
3. 先自测任务卡的正确例子与相关失败场景，记录运行平台、命令和结果。已有检查结果可以复用；没运行的检查写明原因。
4. 用 [PR 模板](templates/pull-request.md) 交接，PR 目标为本校仓库的 `main`。至少一人复看需求与结果；实质改动使用 [adversarial-audit](skills/adversarial-audit/SKILL.md)，独立 reviewer 可承担代码复看，需求负责人确认体验例子。
5. 处理复看发现的实际问题，补充对应验证，再按仓库权限合并。审计结论不代替合并或生产发布授权。

纯文案、注释或微小样式可以人工快速复看；无需每次启动多人审计。常规实质改动用一名独立 reviewer，涉及多个关键风险时再用两到三名。

## 哪些改动多看一眼

按实际改动选检查项，不要求每个 PR 全部重跑：

| 改动 | 有针对性的确认 |
| --- | --- |
| 账号、权限、组队 | 正常用户可操作；跨活动、跨队、越权角色不能读写；服务端也校验权限 |
| 报名、提交、截止时间 | 服务器时区与页面提示一致；截止前后边界、重复点击或重试结果明确 |
| 上传 | 授权、大小与类型限制、文件访问范围、失败提示；用合成文件验证 |
| 评分 | 评委权限、分值规则、重复提交和汇总一致性；页面与服务端按同一已确认规则处理 |
| 数据迁移 | 在合适的测试数据上验证升级和现有数据兼容；记录失败恢复办法与未验证项 |
| 生产配置、发布、备份 | 由部署负责人确认影响、恢复路径与验证结果；恢复验证使用隔离环境 |

关键权限、截止、评分、迁移与生产配置的变更，在操作前审计；操作后核实结果与证据，需要时追加同一审计记录。未获授权的生产写入不因为审计而自动获准。

本机 Linux 脚本、依赖和测试通过 WSL2 Ubuntu、显式工作目录运行；Windows 应用和 UI 检查在 Windows 完成。使用同一源树，分开平台依赖与产物。远端运行按现有部署规范执行，结果注明实际环境。

## 演示、现场与收尾

每周做一次短演示，围绕任务卡的例子展示“现在能做什么、还缺什么、下一步谁接”。现场问题记下角色、时间、操作和可公开的截图；能复现后补进原卡或新卡，不靠聊天滚动查找。

FAQ 与实际界面不一致时随功能一起更新。交接时给出卡、PR、审计记录位置及尚未验证的事项；敏感日志和选手原件留在受限渠道，不放公开仓库。

**[Activity CI](../doc/development-ci.md) 提供基础自动检查。** 提交 PR 后查看运行结果，失败时定位第一条实际错误，修复并补充验证。CI 不替代任务例子、演示、自测与一人复看，也不代表已部署或已验证真实旧数据升级。保持小任务、小 PR，不增加 RFC、双签或量化运维门槛作为开工前置条件。
