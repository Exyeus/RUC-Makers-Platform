# RUC-Makers-Platform 体验改进 SPEC

**状态：提议，待开发小组评审。** 本文包含现状审查、目标流程、实施分包和验收条件；不表示这些改进已经实现。审查日期：2026-11-07（北京时间）。源码基线：`main@119b30210867d7e5c19af5419b05987bafdbbc88`，提交时间为 2026-11-07 09:51:19 UTC+08:00。建议进入仓库后的路径：`doc/experience-spec.md`。

**阅读前提：** 只需理解选手、队长、评委、主办成员、实例管理员的职责，以及“保存草稿、正式提交、检查通过、对外公布”是不同动作。技术实现细节集中在实施说明与证据附录。

## 1. 核心判断与实施次序

当前平台已经具备较完整的业务功能，但多个页面对同一任务的完成状态、下一步和责任人给出不同信号。第一次使用者因此可能“成功点击一个按钮，却没有完成自己以为完成的事”。下一轮最有价值的工作是让任务闭环、状态可信、异常可恢复，并把这些能力组织成不同身份看得懂的工作台。

优先处理四类问题：

1. **正常操作被阻断。** 活动起止时间使用错误保存路径；私有活动的主办登录入口在鉴权前返回 404；默认无邮箱学号账户缺少完整的恢复路径。
2. **成功承诺不准确。** 作品修改后首页仍可能显示提交已完成；上传成功后材料清单仍可能显示缺项；AJAX 保存成功后的离页提示仍声称存在未保存修改。
3. **重要动作容易误解。** 评委“保存评分”可能只保存了不计分的草稿；“保存内容”直接向目标受众生效；移除评委角色会改变已有分数的统计资格。
4. **工作台没有优先回答当前任务。** 新选手先遇到宣传、日历和全站人数；主办方同时看到公共导航与大量后台功能；原生桌面表单和导航多处使用 10–12px 字号。以上分别是已确认控制流、界面语义风险和设计判断，详细证据见审计附录。

| 优先级 | 定义 | 本轮交付重点 |
|---|---|---|
| P0 | 对应业务环节启用前必须解决；正常用户可能被卡住或误判正式提交结果 | 日期保存、私有主办入口、默认账户恢复、作品当前状态与材料状态一致 |
| P1 | 对应环节大规模使用前完成；影响现场收齐材料、评分和非技术成员独立工作 | 明确评分确认、可恢复草稿、队伍申请闭环、发布预览、角色分工、签到与支持、任务化导航 |
| P2 | 核心闭环可用后迭代，或功能启用时再完成 | 高级撮合交互、个人草稿集合、更多自助建届能力、完整视觉精修 |

P0/P1 是实施次序，附录的 HIGH/MEDIUM 是后果严重度；两者不直接等同。高级匹配、并行分会场等能力只有在本届决定启用时才成为相应发布门槛。

### 1.1 现有能力应继续复用

当前已有“我的作品”和手机“作品”入口、提交状态与可下载凭证、上传任务记录、队友查看、分片续传及校验、角色化手机导航、评委独立登录、输入期间暂停现场跟随、版本冲突校验、材料检查、签到、数据导出、私人工单和关键操作日志。上述能力不应被重新写成“待从零建设”。[作品页面][E14]、[上传脚本][E16]、[评委交互][E32]、[手机导航][E47]。

统一深紫品牌和官方素材已经进入所审查的 main；本轮视觉建议基于该版本继续整理。GitHub #82 仍是体验验收与视觉协作入口，不能从它较早的进度文字推断当前 main 仍未合入这些样式。#88 已关闭且找回代码已存在，本轮要求的是补全实际恢复路径。部署 PR #120 仍为草稿开放状态，不算本轮 main 的已交付能力。[品牌样式][E46]、[Issue #82](https://github.com/Exyeus/RUC-Makers-Platform/issues/82)、[Issue #88](https://github.com/Exyeus/RUC-Makers-Platform/issues/88)、[PR #120](https://github.com/Exyeus/RUC-Makers-Platform/pull/120)。

### 1.2 必须明确的产品范围

**当前只放行 `program=maker_camp`。** `program=hackathon` 的枚举本身标注“暂未开放”，公共、管理和评委等活动入口均受同一个门禁限制。本文审查的是现有创客营工作区中已经写出的参赛、作品、评审和管理能力；黑客松正式启用要作为单独的范围决定，不能靠修改活动标题或直接删掉 404 条件代替完整验收。[产品枚举][E05]、[访问门禁][E01]。**本届已定：沿用创客营工作区，门禁不放宽（见 §6.4 第 1 项）。**

**当前按一个活动一个现场队列、同一组有效评委评全部通过检查的作品工作。** 数据模型只允许活动内一个 LIVE 队伍，计分集合来自本届有效评委，除本人队伍外没有按赛道/场次分配的任务模型。如果本届采用两教室并行路演或分赛道评委，必须增加明确的场次与应评任务分配；如果使用统一评委组，则先把该边界写进组织手册。本文不默认本届已采用某一种赛制。[现场约束][E44]、[应评集合][E35]。

## 2. 从各角色任务定义成功

| 身份与压力情境 | 用户真正要完成的事 | 页面必须直接回答 | 可验收的完成标志 |
|---|---|---|---|
| 初来选手：手机打开群内链接，不懂系统术语 | 确认活动、注册/报名、找到队伍、交作品 | 我是谁？报名成功了吗？下一步是什么？何时截止？ | 不靠群聊解释即可找到状态、下一动作和求助入口 |
| 队长：截止前上传大文件，途中网络波动 | 可靠保存并正式提交正确版本 | 文件是否收齐？只是排队还是已提交？哪一版有效？ | 服务器回执、当前材料、队友看到的状态一致；失败能继续 |
| 评委：刚受邀，连续听多队路演 | 找到自己应评项目、记下判断、确认计分 | 正在为谁评分？是否保存？是否已计分？还差谁？ | 任何时刻都能辨认队伍和保存状态；半份判断可恢复 |
| 非技术主办成员：临时接手，没有读开发文档 | 改日程、发布通知、签到、检查材料、催缺评 | 我负责什么？这个按钮影响谁？发布前能否预览？ | 在能力范围内独立完成操作，知道如何更正错误 |
| 管理员/活动负责人：多人协作、临场交接 | 授权、配置关键窗口、排除阻塞、收尾发布 | 谁能做什么？哪些条件未满足？变更会影响多少记录？ | 关键动作有影响摘要和记录；不依赖数据库修改处理日常事务 |

审查中的对抗条件为：用户不预读长手册；用户可能把“保存”理解为完成；会刷新、返回、换设备或短暂断网；管理员会为交接而调整角色；活动接近截止时同时存在草稿、排队、需补充和已通过作品。这些是验收场景，不是声称已经观察到的真实用户行为。

## 3. 信息架构与页面职责

### 3.1 公共宣传页与登录后工作台分别承担明确任务

公共页继续保留“造物有心”的品牌、粒子视觉和活动叙事，首屏同时说明活动名称、对象、时间、地点、当前开放阶段与报名方式。登录/找回密码页聚焦账户任务，手机上让表单优先可达；不要求用户每次恢复账户都先浏览完整宣传内容。

登录后按角色进入任务首页。选手首页的第一张卡固定回答：**当前状态 → 最近相关截止 → 一项主动作 → 最近变更**。例如：“已报名，尚未组队；组队截止 11月X日 18:00；找队伍 / 创建队伍”。日期必须来自配置，不将示例日期固化为赛事规则。“继续我的参赛旅程”替换为“完成报名”“查看入队申请”“提交作品修改”等具体动作。

选手自己的任务卡放在小时历、全站人数、赛道推广与学习推荐之前；主办方首页优先显示“待检查 5 份、缺正式提交 3 队、评分草稿未确认 2 份”等可点击待办。宣传统计保留在公共页或次级区。小时历保留为可选查看方式，默认同时提供按时间排列的“下一件事”，不让小色块成为唯一理解日程的入口。[现有首页顺序][E04]、[固定 CTA][E03]、[总控统计][E38]。

### 3.2 以身份与任务组织导航

| 当前身份 | 默认主要入口 | 次级入口与规则 |
|---|---|---|
| 选手 | 我的进度、我的队伍、我的作品、日程与规则、帮助 | 交流广场、学习、展厅、加分事项进入对应次级区；未启用功能不占主导航 |
| 评委 | 待完成评审、当前路演、已确认评分、评分规则、求助 | 不将参赛报名/加分/建队当作默认任务；作品材料在评分任务内访问 |
| 主办成员 | 我的待办、报名与队伍、作品检查、现场调度、评审进度、内容发布 | 活动设置、成员与权限按授权显示；公共活动页另设“查看活动页面” |
| 管理员/负责人 | 发布准备、成员与权限、活动设置、运行状态、操作记录 | 高风险操作集中且说明后果；部署细节只在管理员需要排障时展开 |

拥有多个身份时显示明确的“当前工作身份”切换器；切换只改变当前工作上下文，不隐式增加权限。现有后台权限、活动隔离和服务端校验继续有效。页面标题、浏览器标题、导航名称一致，表单返回原列表并保留搜索条件。建议主要入口控制在约 5–6 个，是本项目设计目标，不是通用定律。

## 4. 功能与交互要求

### R01 账户、报名与恢复形成闭环

**目标与原因：** 注册创建的是本站账户，参加一届活动还需要报名；当前无邮箱注册与基于邮箱的找回路径没有接上。用户必须知道自己完成的是哪一步，以及无法登录时怎样继续。关联 findings：#[1]、#[2]、#[17]。

- 所有学号登录卡保持一致的注册、忘记密码、工作人员入口。显式写“本站密码”，避免误解为校园统一认证；保留现有不索取校园密码的说明。
- 注册成功即说明“账户已创建，下一步完成本届报名”；完成报名有持久状态、选手短编号和下一动作。必要字段与用于展示/匹配的可选字段分组，可选资料可稍后完善。
- 从组队/回应等任务进入补资料流程，完成后返回原活动内的任务；回跳仍使用已有安全校验，不接受任意站外地址。
- 恢复邮箱作为可选且经过验证的能力，提供可发现的绑定/修改入口；不凭空把邮箱改为参赛门槛。无邮箱者看到实际联系人和可执行的人工恢复说明，不能被要求先登录绑定邮箱。人工恢复只核对必要信息，不能仅凭知道学号重置他人账户。
- 邮件发送失败允许明确重试；不能因为失败前写入请求时间就把用户锁在 24 小时等待中。返回登录使用确定路由。失效链接回到当前活动恢复入口。
- 私有活动使用可完成鉴权的通用入口或匿名可见的登录壳；登录前不展示私有活动内容，登录后校验本届授权再回到草稿管理。不能要求先公开才能准备。
- 评委和工作人员得到可复制的邀请说明：活动、身份、专用入口、初次使用步骤、恢复/联系人。优先接上已有邮箱恢复能力；限时设置密码链接可后续替代人工密码交接。

**验收：** 未登录有权主办人可从私有管理链接完成登录；无权者不可读活动。无邮箱、已验证邮箱、邮件故障和失效链接四条恢复路径都有可执行下一步。新选手完成报名后能在首页明确确认报名状态；评委登录不会被默认引导去填选手报名。

### R02 作品状态、材料列表与提交凭证使用同一份事实

**目标与原因：** “上传完成”“服务器登记”“正式提交”“检查通过”有不同后果。将这些状态准确呈现，比再加一个提交入口更能减少截止前的误操作。关联 findings：#[3]、#[4]。

| 实际状态 | 主提示 | 主动作 | 不能暗示的承诺 |
|---|---|---|---|
| 未创建作品 | 尚未创建作品 | 开始填写 | 不把未创建说成提交失败 |
| 草稿已保存 | 草稿已保存，尚未正式提交 | 补齐材料 / 正式提交 | 不使用“提交成功” |
| 上传进行中 | 海报已接收；录屏上传 60% | 继续上传 / 暂停 | 文件选择成功不等于上传完成 |
| 已登记排队 | 服务器已登记，等待指定材料完成 | 查看进度 / 继续上传 | 有登记凭证不等于已正式提交 |
| 正式提交完成 | 当前版本已正式提交，待检查 | 查看提交凭证 | 不把待检查说成已通过 |
| 已修改未重交 | 有修改尚未正式提交 | 提交修改 | 首次提交时间不能让当前版本继续打勾 |
| 主办方要求补充 | 需补充：具体材料/原因 | 定位缺项并补充 | 不用一句“需要补充”让选手猜 |
| 检查通过 | 当前提交版本已通过检查 | 查看路演安排 | 作品公开仍须单独遵守授权 |

作品页顶部显示作品名、队伍、当前版本、当前主状态、最近一次正式提交时间和下一动作。材料逐项显示现用文件、大小、更新时间、上传/校验结果；当前材料与历史任务分开显示。操作成功后从服务器刷新状态、材料和缺项，保留正在编辑的文字。

**最小实现：** 复用 `Project.state`、revision、服务器回执和现有 manifest，增加统一摘要生成函数，供首页、作品页、队友查看、主办待办与状态接口复用。首页不再仅用 `submitted_at` 判断完成；总控将“从未提交”“已改未重交”“上传未完成”“待检查”“需补充”分开计算。客户端不各自推断资格。

**旧版本的产品规则：** P0 先明确执行当前实现的“修改后需要再次正式提交”，不能宣称旧版仍然具备有效参评资格。建议后续支持“有效正式提交快照 + 独立编辑稿”，新版本提交成功才替换正式版；这需要明确的版本记录和文件保留实现，不能靠一行提示承诺。历史 SHA 和凭证不自动等于历史附件仍可恢复。

服务器登记时间与活动时区作为截止依据；客户端点击时间仅用于异常追溯。主界面把 UUID、SHA-256、绑定时间等放入“查看详细凭证”，保留下载证据能力。对网络中断显示最后一次服务器确认的状态与时间，不自行宣布成功。

**验收：** 首次提交→修改保存→替换附件→排队→正式提交→退回补充，所有身份视图一致；海报上传成功立即清除海报缺项；失败保留现用旧文件；两标签冲突不覆盖最新内容；临近截止的成功判断以服务器状态为准。

### R03 保存、校验和异常恢复有统一交互契约

关联 findings：#[5]、#[11]、#[14]。所有重要编辑表单采用“未修改、未保存、保存中、已保存、保存失败”状态。只有服务器确认某一输入快照后才标记已保存；请求期间继续输入的内容仍是未保存。成功后无新修改不再弹离页警告，失败时保留内容并可重试。

表单错误分为三类：字段不合法时在字段旁解释并给可定位的顶部摘要；权限/截止/版本变化时说明规则和下一步；网络中断结果未知时提供查询状态和重试。不要把确定的字段拒绝统一写成“尚未确认登记成功，请联系技术人员”。使用具体错误例如“Demo 链接需为可访问的公网地址”，同时保留已输入值。

作品和评分草稿应能从一次会话中恢复。对评分优先做服务端部分草稿；对未抵达服务器的输入可使用有期限的本地暂存。缓存按账户、活动、对象与规则版本隔离，恢复前与服务器 revision 比较；会话过期后原账户重新认证可恢复，主动退出则清理本地暂存，此后重新登录只恢复已存到服务端的草稿。不得在公共评委设备上展示上一位的草稿。自动保存可在明确保存契约稳定后增加。

**验收：** 成功保存无多余警告；保存中继续输入仍有警告；网络断开/重登/页面刷新可恢复同一对象的草稿；不能把缺填分数替换成 0 以便过校验；服务端未确认不得显示已保存。

### R04 组队与交流围绕“我的关系”组织

关联 findings：#[6]、#[7]、#[8]、#[9]。保留普通组队与高级匹配两种实现的差异，向用户提供一致的“我的队伍、我发出的申请、收到的邀请、待我确认”视图。普通组队不能因高级匹配关闭就缺少申请进度。

- 申请卡显示目标、时间、待谁处理、结果和允许的撤回动作；加入一队后按明确规则结束其他申请。通知中心只汇总与本人相关的待办和结果，公告作为独立分区，不把装饰圆点伪装成未读数量。
- 单人队长在冻结前有明确退出/解散路径；有草稿时先说明归属和保留策略，不能悄悄删除。多成员队长先交接；冻结或已经进入评审时说明限制并提供带对象信息的求助。
- 正式名单通过可搜索的姓名、学校、短编号选择成员，界面显示人数、资格、本人确认情况；稳定 UUID 留在服务端。名单修改仍应使旧确认失效，发起人不能代替他人同意。
- 运营撮合结果显示人名、想法标题、共同时间、推荐依据、待回应者与下一动作；技术诊断可折叠。未批准政策显示“此功能待负责人配置”，内部方案讨论移出操作区。
- 交流广场增加“我的发布/草稿/回应”。私有草稿离开详情后仍可找回，停止公开后仍在作者列表。人员卡可发私密交流邀请；联系方式继续按双方同意机制处理。

**验收：** 新人申请三队后能自行查到各自状态；单人创建后可有说明地退出再加入别队；三人组队无需手工复制 UUID；私有交流草稿重登后两次点击内可找回；他人仍不可访问私有内容。

### R05 评委以“当前任务与剩余任务”为中心

关联 findings：#[10]、#[11]、#[12]、#[13]。评委首页默认显示“待评 N、草稿 M、已确认 K / 应评 T”，提供待评、草稿、已确认、赛道与关键词筛选，以及下一份未完成任务。所有计数来自同一有效任务集合，退出评审的历史分数另列。

评分表把“保存草稿”和“确认评分并继续”分成两个动作。确认时显示队伍名；草稿提示“尚未计分”，确认提示“已计入统计”。已确认的修改要明确区分“更新已确认评分”与“撤回为草稿”。四项分数允许未填的部分草稿，正式确认才校验完整性；特别奖区就近显示额度和已提名队伍，第四次提名时不要求评委凭记忆找旧记录。

手机把“评分”和“材料”作为可快速切换的区域，长介绍默认折叠；桌面沿用双栏。持续可见的“正在评分：A队”与“现场进行：B队”分开；操作栏不能被软键盘或底部导航遮挡。继续保留输入期间暂停自动跟随、原项目绑定、规则版本和评分 revision 校验。

主办端提供缺评明细或作品×评委矩阵，区分未评、草稿未确认、已确认与已配置的回避/任务分配例外。当前已有本人队伍回避；其他例外必须来自正式确认的规则，不增加随手绕过完整性检查的“豁免”按钮。评委访问权限与计分资格明确分开：停止访问不能默默撤销既有有效分数；评分开始后新增/移除计分资格须展示影响项目、评分和缺评数量，并记录原因。公布后保持现有锁定。

如果确认采用分赛道/分会场评审，新增活动内评分任务分配与场次范围，按任务算应评数；不要通过删评委、临时放松完整性校验来凑齐发布条件。

**验收：** 80个合成项目中仅1个待评、2个草稿，评委两次操作内能定位；只填一项分数可存草稿但不能确认；A队未存时现场切到B队，不丢输入、不改变保存对象；移除/新增资格之前能看到对结果的影响。在已采用并实现按赛道/场次分配时，非本人应评范围的任务不会成为发布阻塞。

### R06 主办方配置与发布可预览、可理解

关联 findings：#[0]、#[14]、#[20]。优先为已创建的工作区提供“发布准备”清单：基本信息、时间与截止、赛道与材料要求、工作人员、各身份预览、发布。创建新一届的完整向导可以后置，不要求本轮重做上游 Eventyay 活动系统。

活动日期和截止字段分别保存到所属模型，并在同一事务中处理，成功后显示最终值。保留现有时间顺序校验；改期时列出与新日期不一致的截止和日程，让主办人选择处理，不自动平移全部时间。报名/建议提交/正式截止/材料冻结分别配一句用户后果说明。

公告、教程、赛题和日程增加草稿、已发布、已归档的生命周期，分开“保存草稿”与“发布/更新公开版本”。发布前展示真实模板预览、受众和生效范围；修改已发布内容先说明是否覆盖公开版。归档保留引用，已被队伍使用的赛道不直接删除。

“开放活动”“开放评分”“开放展厅”“公布成绩”作为独立操作，从相关任务页进入，显示前置条件、影响范围和具体结果。改地点或文案不同时改这些开关。成绩发布页列明缺评者、即将公开的作品/名次/评语范围；空缺仍须由现有后端规则阻止发布。

**预览要求：** 提供游客、新选手、已组队、已提交、评委等待等合成状态。始终标识预览；预览不能伪装成真实用户会话、绕过权限或写入真实报名/作品/评分。对需要演练写操作的情况，使用独立演练活动与合成账户，而非在真实活动上仅加“演练”字样。

**验收：** 非技术主办成员可独立改期并找出不一致日程；保存草稿不在公共列表/直达页出现；预览不发布；公布前实际范围与预览一致；表单返回原列表，未保存离开有保护。

### R07 权限和交接对应实际分工

关联 findings：#[17]、#[19]。现有鉴权真实存在，但“主办方”授权较粗，评委/志愿者标签不能完整表达内容维护、签到和只读查看。先映射下列实际能力到现有账户、Eventyay团队与活动范围，再按本届分工提供预设角色；不新建独立账号体系。

| 工作角色 | 默认能力 | 需另行授予的能力 |
|---|---|---|
| 内容维护 | 公告/指南/日程草稿与授权范围内发布 | 成绩发布、成员授权、全量个人信息导出 |
| 签到与材料检查 | 查本人负责范围、签到、材料检查与回复 | 活动关键设置、评分资格变更 |
| 现场调度 | 就绪、开始/暂停/结束/更正及队列 | 改分、公布成绩、成员授权 |
| 只读观察 | 查看授权的活动进度 | 任何写操作及非必要个人信息 |
| 活动负责人 | 授权、关键窗口、发布、更正审批 | 实例级配置仍属于管理员 |

页面显示当前身份和本届权限，邀请/交接卡说明入口和“能做什么”。权限不足页面给出清楚原因、联系负责人和返回入口；错误页不能泄露其他活动的数据。预览权限不等于真实代操作权限。后台附一页任务式速查：发布通知、改日程、帮助选手、检查作品、确认缺评、交接现场；每条链接直达页面，注明成功后的状态和常见恢复办法。

**验收：** 内容成员不能发布成绩；只读成员不能写；撤回某届权限立即生效且不波及另一届；被授权者不需要学习内部权限字段名即可找到自己工作。

### R08 名单、工单与导出便于现场处理

关联 findings：#[15]、#[16]。统一显示“姓名 + 本届短编号 + 队伍”，在有权限且需要核对时显示学号/邮箱；无邮箱不是缺身份。导出使用稳定ID、姓名、学号和可选邮箱，不能把邮箱当唯一交接标识。

签到成功后“已签到”变成状态，撤销是明确的次级动作；重复签到幂等。保持搜索条件与位置，同名人员可区分。作品检查、缺交、待评分和工单列表保留筛选、排序和返回上下文，状态计数与列表使用同一筛选条件。

工单支持在同一条目追加消息，保留每次回复、处理人和时间；区分待主办处理、待选手补充、已解决。创建时可自动附带有权限的队伍/作品、发生时间和错误类别，用户可检查附带内容；不要自动上传作品原件、令牌或隐私数据。收到回复进入站内待办。

材料包导出显示范围和内容说明；大包生成使用可查询的任务或明确准备状态与失败重试，避免将反复点击下载当作恢复办法。最终下载仍鉴权。此项是容量体验改进，不宣称本轮已完成并发或存储压测。

**验收：** 学号账户报错后主办能从工单直达对应作品；连续两次回复都可追溯；同名无邮箱志愿者导出可区分；搜索签到后仍留在该搜索；重复点击不会撤销签到。

### R09 现场操作有明确影响和可控恢复

关联 finding：#[21]。调度页突出当前队伍、下一队、计时状态、材料就绪与同步时间，确认“结束”时带具体队伍。已有结束确认、暂停、继续、顺延、设备检查与断网提示保留。

增加负责人专用的“更正误结束/重新排入”，说明恢复计时方式、记录原因，不改已保存评分、不破坏单一LIVE约束；不通过手工改数据库恢复。播放助手的“查看连接说明/复制服务地址等非秘密配置”和“更换连接令牌”分开，更换前说明旧连接将失效；生成成功后给出明确重新连接步骤。原令牌只在生成当次显示和复制，服务端仅存摘要，刷新后不承诺重显；丢失后走明确的轮换流程。连接状态要能区分未连接、最近同步正常、连接中断和已过期。

**验收：** 合成现场中误结束后，负责人能在明确流程内恢复或重新排入；两位操作者同时开始不同队伍仍只有一队LIVE；单纯查看教程不轮换令牌；网络中断时不显示伪造的正常倒计时。

### R10 视觉、字体和文案为任务让出位置

**源码依据：** 桌面 `hub.css` 的导航、表单标签和输入多为12px，旅程说明与动作多为10px；移动样式已将许多输入提升为16px、按钮提升为44px。小时历每行24个格子且最小宽度360px，在手机上可能需要横向查看。不能概括为“全站字号一样小”或“完全没有手机适配”。[桌面字号][E42]、[旅程字号][E43]、[移动样式][E48]、[小时历][E45]。

以下为本项目拟采用的设计与验收目标，不是已测出的改进效果：

| 元素 | 建议规格 | 使用规则 |
|---|---|---|
| 正文、表单输入 | 16px起，行高1.6–1.8 | 评委与主办工作台优先保证持续阅读；不要依赖浏览器放大才能读懂 |
| 导航、字段标签、表格关键列 | 14–16px | 关键截止、错误和状态不能使用装饰字号 |
| 辅助信息 | 13–14px；12px仅用于非关键元数据 | 服务器状态、提交结果、权限限制不是脚注 |
| 页面标题 | 24–32px；小标题18–20px | 标题直接命名任务，宣传标题可另用大字 |
| 操作目标 | 主要触屏操作至少44×44px | 紧凑图标有文字/可访问名称，不能只有模糊符号 |
| 数字 | 等宽数字、单位就近 | 分数、人数、倒计时与时间范围便于比较 |
| 内容宽度 | 说明正文约32–42个汉字宽，或60–80个拉丁字母宽，需实机调整 | 表格可使用更宽区域；避免大屏一整行长说明 |

中文工作界面使用统一系统无衬线字体栈；现有宋体类标题可以保留在公共宣传页。英文口号、代码窗、星号、渐变、粒子效果不参与任务状态表达。延续现有品牌色；后台优先使用稳定的实色表面，减少同时出现的背景图、透明叠层和渐变卡片。可在测试后评估浅色或高对比工作模式，不把增加主题切换当作本轮P0。

把标题“全局清晰，现场从容”改为“活动总控”，把“每个人，都有自己的坐标”改为“报名与签到”，把“看见作品，也看见可能”改为“评委工作台”；原句可作次级说明。表单按钮去掉无意义的统一 ↗：站内下一步用明确动词，外部链接才保留外跳标记。后台折叠“继续你的创造之旅”等长期推广卡片；保留必要品牌署名。来源模板见[总控][E39]、[名单][E40]、[评委目录][E31]、[共享壳][E41]。

小时历与缺席时间选择提供可读列表/时间段输入作为等价方式；色块有文字说明，键盘可用。图表式控件不能为了紧凑让用户精确点击极小格子。错误提示有文本与字段定位，成功/等待/失败不只靠颜色区分。

**验收：** 390px手机、768px平板、1366/1440px桌面与200%缩放走查；Windows和手机系统实际验证中文回退字体；主要任务无需横向滚动；软键盘与底部栏不挡主动作；键盘可完成登录、提交和评分；减少动态效果偏好仍有效。对比度需测量实际渲染颜色，不仅看CSS变量；本轮不声称已完成对比度或无障碍认证。

| G 组队与交流闭环 | R04普通模式、单人退出、个人草稿 | A/C | 申请有结果，自己建队后有退路，草稿可找回 |

| I 条件功能与精修 | 高级名单选择、撮合可读化；若需要则做分会场任务；视觉深化 | 仅按本届确定范围启动 | 开启的高级功能同样能由新手独立完成 |

**本届范围定案：** I 包的高级匹配与撮合可读化本届不启动（§6.4 第 4 项），高级匹配仅作运营内部工具；R04 以普通组队的申请与退出闭环为准。
技术路径继续使用 Django模板、现有forms/服务层及原生JS/CSS。无需为本轮体验改进迁移到新的前端框架或另造一套管理系统。代码改动分别覆盖其失败条件；排队上传、权限、截止、评分和事务仍以服务端为准。

**与现有工作对齐：** C/E的页面语言与品牌延续 #82；A中的恢复作为 #88/#89 已有功能的后续修复，可新建关联缺陷，不把已实现功能重新立项；对象存储与生产部署继续由 #85/#120 承接，B仅要求其上传/替换结果保持相同用户语义。本文没有代为创建Issue、提交PR或修改源仓库。

## 6. 验收方式与测试情景

### 6.1 用完整任务验收

| 编号 | 合成情景 | 必须观察到的结果 |
|---|---|---|
| T01 | 新选手从公共链接注册、完成报名 | 清楚区分账户与报名；首页显示本届状态和下一步 |
| T02 | 学号无邮箱、邮件失败、重置过期 | 每条路径有可执行下一步；失败后可合理重试；返回链接有效 |
| T03 | 私有活动，匿名有权主办人/无权账户分别进入 | 前者能登录管理，后者不可读私有内容 |
| T04 | 只改开始、只改结束、同时改名称与日期 | 正确保存到相关模型；非法顺序字段报错；失败不部分保存 |
| T05 | 提交后保存修改、再替换海报 | 首页/作品/队友/后台共同显示待重交；附件与缺项即时一致 |
| T06 | 上传中断、取消、恢复；截止附近排队 | 显示最后服务器确认；任务可继续；登记与正式提交不混淆 |
| T07 | AJAX成功后离开、保存失败后离开、保存中继续输入 | 仅真正存在未保存输入时告警；字段错误定位准确 |
| T08 | 普通模式发出多队申请，再撤回或入队 | 申请者可查全部结果；不靠重复点申请探测状态 |
| T09 | 单人队长希望改入另一队 | 冻结前有清楚退路；草稿不会静默删除；冻结后解释限制 |
