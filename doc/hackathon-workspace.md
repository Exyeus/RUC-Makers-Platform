# 黑客松一体化工作台

工作台直接运行在 Eventyay 的 Django 应用中，使用现有账户、活动、PostgreSQL 和会话系统。入口为 `/hackathon/`。存在公开且尚未结束的黑客松时，网站首页会进入最近一届的工作台，现有活动列表、票务和会议功能仍可通过原路由访问。

## 初始化黑客松

初始化、迁移和公开活动是独立操作。`start-local.sh` 只检查迁移状态，不自动迁移、创建或公开工作区。先确认当前配置连接的是开发数据库，再执行下列命令。

升级到 `0012_isolate_existing_hackathons` 会将升级前所有工作区的 `program` 写为历史隔离值 `hackathon`；这些工作区的参与者与管理入口目前均返回 404。升级前应备份并确认旧活动的访问安排；初始化新活动不会复制旧活动数据。界面更名不更改此数据隔离规则。

在 `app/` 目录、已配置好项目数据库与 Redis 的环境执行：

```bash
.venv/bin/python manage.py migrate
.venv/bin/python manage.py setup_hackathon \
  --organizer hackathon \
  --event tongzhou26 \
  --slug tongzhou26 \
  --name '人大通州黑客松' --program maker_camp \
  --start-date 2026-10-21 \
  --publish
```

日期仅作命令示例，替换为正式日期。省略 `--start-date` 会生成 30 天后的筹备排期；省略 `--publish` 会保持活动私有，同时把初始内容全部留为草稿。带 `--publish` 时初始指南、赛道、日程与公告直接标为已发布，选手端立即可见；不带时需要在“内容管理”逐条点“发布 / 更新公开版”。命令可绑定已有 Eventyay 活动，也可创建新的活动；同一工作台已存在时不覆盖其数据。每届使用不同 `--event` 和 `--slug`。初始内容含 8 篇可编辑指南、2 条示例赛道、2 天的筹备日程与明确标注待确认的公告，不生成虚假参赛人数、作品或成绩。

已有 Eventyay 实例管理员可以进入 `/hackathon/tongzhou26/manage/`。非实例管理员必须属于该活动主办方的管理团队，拥有 `can_change_event_settings` 且有该活动的访问权限。普通 `is_staff` 标记不授予活动管理权限。全新安装可使用项目原有的 `manage.py create_admin_user` 设置管理员。

从旧活动切换到黑客松时，原来只被授权管理旧活动的团队不会自动获得新活动权限。需要沿用同一主办方的管理团队时，可显式复制其活动访问授权：

```bash
.venv/bin/python manage.py setup_hackathon --slug tongzhou26 --copy-organizers-from next
```

将 `next` 替换为来源工作区标识。此选项也可在首次初始化时传入，或对已有黑客松重复执行；已有内容不会被覆盖。只为同一主办方下拥有来源活动访问权和 `can_change_event_settings` 的管理团队添加目标活动访问权，不复制选手、评委或志愿者角色，不修改实例管理员权限或 `all_events`。

主办方使用 `/hackathon/tongzhou26/account/organizer/` 登录，验证成功后进入活动管理。登录后各页面右上角保留“主办方后台”入口，手机上显示为设置图标按钮；侧栏和手机底部导航也保留管理菜单。原来的 `/login/?next=/hackathon/tongzhou26/manage/` 链接也会转到此入口。学号登录和邮箱登录页面可以互相切换；所有登录后的页面右上角都有“退出登录”，手机端同样显示。退出后回到黑客松登录页，清除当前会话；切换主办方账户时可使用“退出并切换账户”。

活动未公开时，公众页面仍返回 404，但主办方与评委的登录入口保留一个不含任何活动信息的通用登录页（标题、简介、场地、日期均不显示），完成登录且确有本届权限后才进入管理页；登录失败的提示同样不带活动内容。未获授权的账户即使已登录，也只能继续看到 404。

开发运行沿用 Eventyay 配置。部署时使用现有静态文件构建与收集流程；新增资源位于 `eventyay/static/hackathon/`，无需新增前端构建工具。临时预览可使用：

```bash
.venv/bin/python manage.py runserver
```

从另一台电脑预览时，`localhost` 指向访问者自己的电脑。请使用开发机的局域网 IP，并将 `EVY_SITE_URL` 配成相同地址，否则站点的域名校验会返回 400。以下是当前开发机的启动示例（在 `app/` 下执行，需本机 PostgreSQL 和 Redis 已运行）：

```bash
EVY_POSTGRES_HOST=127.0.0.1 EVY_POSTGRES_PORT=55432 \
EVY_POSTGRES_USER=tianjiaming EVY_POSTGRES_DB=eventyay-db \
EVY_SITE_URL=http://10.77.110.167:8000 \
EVY_SHORT_URL=http://10.77.110.167:8000 \
EVY_TALK_HOSTNAME=http://10.77.110.167:8000 EVY_DEBUG=false \
.venv/bin/python manage.py run_hackathon_preview 0.0.0.0:8000 --insecure
```

浏览器打开 `http://10.77.110.167:8000/hackathon/tongzhou26/`；开发机 IP 变化时同步替换启动配置和访问地址。`--insecure` 仅用于本地预览的静态资源服务，正式部署使用现有部署流程。

正式发布前，在“活动设置”确认活动起止时间、场地、组委会联系方式、队伍人数、所有截止时间和路演时长，在“内容管理”逐条发布日程、赛道、指南与公告，最后在“发布准备”（`/hackathon/tongzhou26/manage/publish/`）核对清单并单独开启四个发布开关。活动起止时间、各项截止时间和每条日程分别维护；保存改动起止时间后，页面会自动列出落在新活动窗口之外的截止时间与日程条目，但不会自动顺延任何时间。日期输入与显示均使用关联 Eventyay 活动的时区。

## 黑客松名称与交流

当前平台服务黑客松。当前活动地址为 `/hackathon/tongzhou26/`，旧 `/hackathon/camp/` 跳转到相同页面的新地址。数据库的 `maker_camp` 与部分静态资源文件名是历史技术标识；界面、邮件和初始化默认内容统一使用“黑客松 / HACKATHON”。工作区更名只修改 URL 标识，保留关联活动、原有数据和入口权限。`program=hackathon` 仍属于迁移 `0012` 的历史隔离值，其页面、API 与现场令牌接口保持 404；请勿通过切换 program 来更名。

组队页面提供展开的内容形式、赛道与伙伴关键词筛选，关键词按分类展示，选择后统一应用或清除。个人资料入口继续使用右上角头像；手机端通知可从“更多”中的“通知公告”进入。登录后的首页为深色参赛工作台，主任务随真实报名、组队、必读阅读与作品状态变化，排队上传、待补充、正式提交分别提示。没有必读文章时，阅读项视为已完成；必读推荐不增加作品提交门槛。已完成事项可展开查看与修改，作品与回执入口始终保留。

截止时间来自当前活动并显示关联 Event 的时区；报名或组队冻结后，主任务转到支持入口。作品截止后指向回执或支持，成绩公布后指向结果。能否修改作品仍由作品页和服务端现有规则判断，路演或确认评分可能提前锁定作品。首页的活动累计人数、队伍数和正式提交记录数不代表个人进度。

首页保留参赛指南、作品展厅、帮助与角色工作台；活动小时历移入可展开区域。每格代表一小时，活动与重要截止分别着色，悬停、键盘聚焦或点按可查看该小时全部安排；数据来自活动截止时间与主办方维护的日程。导航沿用原有手机抽屉，支持 Tab、Esc 和关闭后返回触发按钮。工作区各页共用 `.ruc-app` 主题与分组侧栏，活动日程、通知公告、学习与指南、组队、作品、支持及角色工作台切换时保持一致；导航根据当前页面及详情所属栏目高亮。访客宣传与登录入口保留独立布局，路演全屏仍隐藏导航。

设计依据、状态例子与验证记录见 [参赛工作台 UI 重构](ui-workbench.md)。

组队广场整合交流与共创、作品池、找队友，以及启用匹配后的推荐和名单确认。支持灵感、经历/痛点、开放问题、展示/开发日志、求助、微型共创和招募七类卡片，卡片可附作品、图片或录屏链接，并注明希望怎样回应。作者可关闭回应或保存为非公开草稿；回应默认私密，仅发布者、回应者与主办方可见。发布、回应不自动获得录取加分。

个人资料和匹配资料提供活动前两天的小时格子，桌面可拖动连续圈选，触屏和键盘可逐格勾选。只有活动起止时间内的完整小时可选。具体缺席时段不公开；匹配页明确确认安排后，将剩余小时换算为现有匹配引擎的半小时时段。已确认匹配时间的参与者更新报名时段时，会同步匹配时间并使旧推荐失效。

加分规则由主办方在“内容管理 → 加分规则”配置事项、分值、证明标准并公布。参与者每个事项限申请一次，主办方在“加分规则”页面填写审核说明并通过或拒绝。通过时记录当时分值；重复请求和后续规则改分不会重复计分。黑客松参与加分独立于作品评审分数。未配置时展示“待公布”，不预设未经确认的分值。Token Panel 保持待定。

## 将旧活动地址改为 tongzhou26

在 `app/` 中使用既有配置执行：

```bash
.venv/bin/python manage.py rename_hackathon_workspace camp tongzhou26
.venv/bin/python manage.py rename_hackathon_workspace camp tongzhou26 --apply
```

第一条只预览；第二条以事务和行锁修改指定工作区的 `slug`。新标识必须合法且未被其他活动占用；`camp` 是兼容入口的保留标识，不允许新建或改入。命令不创建新活动，不修改关联 Event 的标识、program、时间、用户、队伍或材料。部署本版本与此更名操作需一并安排；如果原工作区已更名，直接使用新地址，不要重复创建。

系统生成的页面导航、表单、登录回跳、上传接口、现场接口与下载地址均从当前工作区生成。旧 `/hackathon/camp/` 及其子路径保留兼容跳转：GET/HEAD 使用 301，POST 等使用 308，保留子路径与查询参数；仍由新地址执行原来的身份验证、CSRF 和活动范围检查。已配置的现场伴随工具建议把地址更新为 `/hackathon/tongzhou26/station/state/`。

## 更新已有活动的默认名称

模板更新不会覆盖数据库中已保存的标题。主办方可在“活动设置”和“内容管理”修改自定义名称、介绍、公告与指南。

对于初始化时保留下来的旧默认内容，可在 `app/` 目录对指定工作区执行：

```bash
.venv/bin/python manage.py refresh_hackathon_branding tongzhou26
.venv/bin/python manage.py refresh_hackathon_branding tongzhou26 --apply
```

第一条只列出匹配字段，不保存；第二条在事务中更新。范围仅为：精确匹配的默认活动名称及关联 Event 名称、默认介绍、默认欢迎公告标题，以及两篇默认指南标题。默认活动名统一为“人大通州黑客松”；关联 Event 的自定义语言名称不变。命令保留其他工作区、自定义标题和正文、选手发布内容、旧审计记录、学号账户、活动标识、program、时间与权限，重复执行不会再次改动。它不会创建或公开活动，也不修改历史迁移。

扫描界面关键词时，同时核对访客首页、登录/注册/找回密码、报名与队伍表单、社区详情、匹配资料和撮合后台、公告与学习资源、加分页面、浏览器标题及邮件标题。历史技术标识、作者自己的历史叙述和“中国人民大学创客协会”组织名称不作品牌词替换。

## 手机与平板访问

使用同一个网址，页面按屏幕宽度自动适配，无需安装或切换版本。手机采用单列卡片和按身份显示的底部常用导航，完整功能位于“更多”或左上角菜单；主办方名单、作品检查、路演队列和成绩表在手机上逐条展示全部字段，原有签到、审核、调度和评分按钮仍可操作。平板采用可展开导航和多列布局，评分时可并排阅读作品材料与填写分数。

触屏布局增加按钮点击区域和输入字号，适配横竖屏以及屏幕安全区域。菜单支持点击遮罩、关闭按钮或 Escape 关闭，并将键盘焦点限制在展开的菜单中。桌面、手机、平板共用账户、数据和原有业务流程。

| 主办方 | 活动总控 | 进度统计、缺交名单、特殊时段、未处理工单、操作日志、数据与材料导出 |
| 主办方 | 内容管理、发布准备 | 通知、日程、指南与赛道的草稿/发布/归档、只读预览、发布前清单、四个发布开关 |
| 主办方 | 选手与队伍、作品检查 | 签到与撤销签到、材料审核、设备演练确认、异常补录、奖项与孵化资源记录 |

| 评委 | 评委入口、现场打分、全部评审 | 跟随当前路演、同页查看海报与作品、回看其他队伍、保存草稿、确认与特别奖提名 |

### 学号账户与个人资料

选手在活动首页 `/hackathon/tongzhou26/#join` 的登录卡片登录，或从卡片进入 `/hackathon/tongzhou26/account/signup/` 注册，填写学号、姓名、邮箱和本站密码；`/hackathon/tongzhou26/account/login/` 会跳转回首页登录卡片，全站只保留这一个选手登录入口。学号支持 4–32 位数字或英文字母，统一转为大写，在本网站全局唯一；前导零保留。学号和原有 Eventyay 用户一对一关联，存入 PostgreSQL，密码使用现有密码哈希机制。数据库唯一约束防止并发重复注册；登录按学号和来源 IP 限制尝试次数，保留原有账户停用及双因素验证逻辑。原邮箱账户仍可使用原登录入口。

学号是本站登录标识，尚未对接校园统一身份认证，不代表已经核验在校身份。多学校联合举办时需要先约定学号命名规则，避免不同学校同号。邮箱用于自助找回密码：登录卡片的“忘记密码”按学号发送重置链接，链接 24 小时内有效，重置后原登录会话失效；24 小时限频从邮件真正发出后开始计算，发送失败时本轮不计数，可立即重试。邮箱可在注册时填写，也可在个人资料页绑定或更换，同一邮箱不能被两个账户使用。未绑定邮箱的账户无法自助找回，页面会直接给出组委会联系方式，并说明需核对学号与注册姓名；管理员核验身份后运行 `.venv/bin/python manage.py reset_student_password <学号>`，在终端隐藏输入新密码，不会仅凭学号改密。主办方在名单中可查看、搜索和导出学号，公众看不到学号或联系方式。

点击右上角头像进入个人资料，可按开发、AI、设计、研究、硬件、关注的问题、兴趣、性格和协作期待添加标签，数量不限，也可自定义标签（每个最多 40 字）。还可填写 120 字以内的一句话介绍，并保留详细技能与项目想法。只有主动开启公开展示且尚未入队的选手会出现在组队广场。广场支持关键词筛选，并搜索姓名、介绍和技能。

### 作品提交

1. 队长保存草稿，获得作品编号。
2. 上传电子海报（PNG/JPG/WebP，最大 20 MiB），可选文稿（PDF/PPTX）、录屏（MP4/WebM）和附件（ZIP/PDF，分别最大 512 MiB）。项目卡必须是电子海报，不能用立牌照片替代；该内容质量由工作人员人工检查。
3. 提供代码仓库、已实现功能说明、Demo 或录屏、备用链接或录屏、实机演示步骤，完成自查。
4. 点击“正式提交”，确认状态和首次提交时间。单独上传不等于正式提交；后续替换附件会重新进入待补充状态，需再次提交和检查。

提交采用版本号防止旧页面覆盖新内容。同一版本、相同内容和操作的紧邻重试不增加版本号。上传检查文件类型、大小、基本格式、图片有效性、ZIP 路径和解压体积；压缩包最多 20,000 个条目，目录元数据不超过 4 MiB，声明解压大小不超过 2 GiB；不接受分卷 / ZIP64 归档。附件存放在 `DATA_DIR/hackathon-private/`，不提供直接媒体 URL，只通过检查权限的下载视图读取。请确保 Web 服务器没有把整个 `DATA_DIR` 作为公开目录，并将该目录纳入备份。公开展厅只可读取授权作品的海报，不公开文稿、录像和源代码附件。其他链接由队伍主动授权公开。

作品的“当前状态”只由 `services.project_status()` 计算：参赛总览的下一步与作品卡、作品页横幅与状态徽章、提交状态面板以及 `project-status` JSON 共用同一份取值和文案，任何视图都不自行用 `submitted_at` 推断。`Project.state_reason` 记录 `changes` 的三种成因——`edited`（保存修改或替换材料后未再次正式提交）、`upload`（排队登记因取消或超时而中止）、`review`（主办方要求补充）；字段上线前的历史记录为空，页面按“需要补充 · 未标注原因”保守展示，不猜测原因。`submitted_at` 只表示首次正式提交时间，因此首页作品数、主办方面板的“当前有正式版本”与“尚未提交的队伍”名单均以 `state` 为准，作品检查页可按 `?state=changes&reason=` 按原因筛选，CSV 增加“状态原因”列。部署需运行 `python manage.py migrate hackathon`。

用 JavaScript 保存作品时，反馈区分“服务器明确拒绝”和“结果未知”：400 JSON 的 `error` 是整体原因、`fields` 是字段级消息，分别显示在状态行与对应输入框下方，页面输入原样保留可直接重试；网络中断或超时则提示尚未确认登记成功，需要先查询状态。请求期间又输入了新内容时，离开页面的确认提示不会被清除（`hackathon:saving` / `hackathon:saved` 事件约定）。上传完成后 `project-status` 返回的 `materials` 与 `gaps` 会就地重建右侧材料清单和“还有这些准备未完成”，无需刷新页面，也不会丢失左侧尚未保存的表单内容；清单文本一律按纯文本写入，不拼接 HTML。带签名的提交回执载荷保持原有字段，新增的状态文案不参与签名。

### 大文件传输与存储

浏览器先登记上传意图，再在 Web Worker 中分段计算 SHA-256，以 8 MiB 分块上传，不把整个文件放进内存。服务端写入私有临时目录，每块完成 `fsync` 后才更新 PostgreSQL 中的接收偏移量。任务允许暂停、自动重试和刷新后重新选择原文件续传；保留至登记后 24 小时或材料冻结时间，以较早者为准。完整文件再次计算 SHA-256，与浏览器指纹匹配后才归档。正式提交允许登记等待尚未完成的上传，详见下文“截止前排队提交与凭证”。

同一作品同类材料仅允许一个进行中的任务。重复启动同一文件返回已有任务，重复分块比对内容，乱序或冲突返回 409。完成请求可重复调用，重复文件不反复增加作品版本号。新材料写入并校验成功前保留旧材料；替换提交后才删除旧文件。进程在分块写入与数据库提交之间退出时，下次请求按数据库确认的偏移量截断未确认尾部。硬链接发布到最终目录，避免额外复制整个文件；临时目录和最终目录必须位于同一个支持硬链接的文件系统。

存储路径按 `活动 ID / 队伍 UUID / 作品 UUID / 材料类型 / 唯一文件名` 分层。下载名称自动生成 `队伍编号_作品编号_材料类型_校验摘要.扩展名`，数据库和作品页保留原文件名。每类材料保留当前有效版本，操作日志保留更换记录。下载支持 `Range`、`If-Range`、`ETag` 与 `HEAD`；Django 在 WSGI/ASGI 下都使用分块读取，供断点下载及录屏拖动使用。ASGI 下采用异步迭代器，避免同步文件响应被整体读取（参见 [Django 流式响应说明](https://docs.djangoproject.com/en/6.0/ref/request-response/#streaminghttpresponse)）。

仓库 Nginx 示例的 `client_max_body_size 10m` 足以承载默认 8 MiB 分块；保留此限制即可使用网页大文件上传。建议代理读取超时至少 120 秒，给最终校验留出时间。禁用 JavaScript 的普通表单上传及主办方补录仍使用整个 multipart 请求；如需让这些入口也接收 512 MiB，可仅对对应上传路由设置 `client_max_body_size 520m`，并确保代理/Django 临时目录有足够磁盘空间。正式环境应使用 HTTPS、持久磁盘与 PostgreSQL/文件联合备份；多应用实例必须共享同一私有文件目录。文件内容不存入数据库，不支持仅靠临时容器磁盘部署。

建议每小时运行以下命令，过期任务将取消，48 小时以上未被引用的残留文件会清理，上传凭证随活动保留。先使用 `--dry-run` 查看候选文件（命令使用与服务相同的数据库和 `DATA_DIR` 配置）：

```bash
.venv/bin/python manage.py cleanup_hackathon_uploads --dry-run
.venv/bin/python manage.py cleanup_hackathon_uploads
```

启动新任务时检查可用磁盘与当前活动已预留的上传体积，磁盘写入失败返回可重试错误，不覆盖旧材料。实际并发能力仍取决于磁盘、带宽与服务进程配置；活动前应按预计队伍数进行压测。

本地预览使用上面的 `run_hackathon_preview` 命令，使普通 HTTP 请求使用 WSGI，并正确提供开发静态资源。当前 Daphne 开发服务的输出缓冲在大文件下载时可能显著增加内存，即使应用本身逐块读取；正式 Docker 配置已将普通 HTTP 交给 Gunicorn WSGI，WebSocket 单独交给 Daphne。

建议提交时间用于留出检查窗口；最终提交截止后选手不能新建上传或修改作品文字，截止前已登记的上传可以在凭证期限内续传。主办方可从作品检查或选手名单进入异常补录，必须填写原因与发生时间，系统记录操作人、版本和原因。材料冻结后拒绝补录。已经开始/完成路演或已有确认评分的作品不能修改参评版本。

### 支持工单与身份交接

工单按逐条线程记录：开单内容、选手补充和组委会每一轮说明都单独保存并按时间排列，不会被后来的回复覆盖。主办端每条工单显示“姓名 · 本届编号 · 队伍”身份行，邮箱只作为旁边的联系方式，避免同名或无邮箱账户无法区分；未报名的账户退回到“姓名 · 账户 #编号”。工单卡和处理页附带该队当前作品的入口，没有作品时给出按本届编号查名单的入口，学号账户报的错可以直接走到对应作品。状态为待主办处理 / 处理中 / 待选手补充 / 已解决，四种状态各有配色，主办端可按状态筛选；总控给出“工单待主办 / 等选手补充”两个数字，前一个与卡片点进去的 `?state=open` 列表是同一份筛选结果，等选手补充的不算进主办待办。回复工单是显式动作，缺少动作标记的提交不写入任何内容。

“待选手补充”的工单在参赛总览里持续可见：帮助面板始终列出等本人回复的工单，并直接指向帮助与支持页。“下一步”一栏先让给报名、组队、截止与上传/材料补充这些参赛动作，作品已提交或只剩阅读推荐时才由工单顶上；成绩公布后两者都不再出现，也不再为此查询。选手在同一页追加说明后工单自动回到待主办处理，这条提示随之消失。选手只能追加自己开出的工单，追加说明与新建工单是两个动作。历史工单的单条“处理说明”由工单线程迁移搬进线程：旧数据没有逐条回复的写入时间，搬过去的发言按工单最后修改时间挂回线程；有处理人的记为组委会发言，没有处理人的退回开单人本人、不标成组委会。该迁移会删除旧列且不可逆，部署顺序必须是先停旧实例、再运行 `python manage.py migrate hackathon`、然后启动新版本；只回滚代码不回滚该列会让旧版本读不到 `reply`。

签到与撤销是两个动作：名单页按当前搜索结果逐行提供“签到”或“撤销签到”，重复签到不再写第二条记录，撤销单独留档；处理后仍停留在同一份搜索结果，未识别的操作不改变签到状态。

导出以稳定依据区分人：志愿者表把负责人与备份的编号、邮箱分成两列，编号优先使用学号，没有学号时使用账户 ID；新增“支持工单交接 CSV”（`manage/export/tickets/`），逐单给出本届编号、账户编号、队伍、作品编号、学号、邮箱、状态、处理人、开单时间、最近沟通时间和沟通条数；账户编号与志愿者表同一口径，未报名的开单人也有稳定依据，邮箱可以为空、只作联系方式。作品检查的处理页保存后回到进入前那份 `?state=…&reason=…` 结果，筛选值只接受枚举取值，异常值会被丢弃。

### 路演与评分

审核通过的作品可加入路演队列，重复生成不会重复排队。通过设备演练后才能标为就绪；同一时间仅一队处于展示中。暂停、继续与开始时间都保存在服务器，刷新页面不会重置；结束展示会记录结束时间。默认 120 秒展示、30 秒评分换场，页面每 2 秒同步；断网时明确标记失联，避免显示过期倒计时。下一队与后两队的候场预览只列出仍通过审核的作品；正在展示的队伍即便材料状态随后变化，现场播放助手仍保留其文稿。顺延和重新排队都必须填写原因：顺延把队伍移到队尾，重新排队将展示中或已完成的场次退回待候场、清空本场计时并保留原顺序位。公布成绩后锁定路演队列，不能再生成、就绪、开始、顺延或重新排队，但仍在展示的场次可暂停、继续或结束以收尾。

评委从 `/hackathon/tongzhou26/account/judge/` 登录，进入“现场打分”（`/hackathon/tongzhou26/judging/live/`）。主办方在路演调度点击“开始展示”后，评委页面每 3 秒同步当前队伍；等待页会自动打开该队的评分表。评分页同时展示海报、完整作品描述、体验步骤、代码及演示链接和附件。可通过队伍选择器、上一队/下一队或“全部队伍与评分”回看；回看模式不会自动跳走，点击“返回当前路演”恢复跟随。

开始输入后暂停自动跟随，换队时显示提示。评分请求始终绑定当前表单的作品，不会错记到新的路演队伍；保存后自动回到当前路演。未保存离开页面会提示确认。草稿可先保存再浏览其他页面，确认后才计入统计；重复或过期表单会提示重新核对，不覆盖其他页面已保存的新分数。断网时保留本页输入并重试现场同步，服务端成功响应才算保存完成。

主办方从“算分规则”（`/hackathon/tongzhou26/manage/scoring/`）配置四项权重，总和须为 100%；每项仍为 0–10 整数分。默认创新性/完成度与实机演示/实际价值/表达为 30/40/20/10，所有有效评委的加权总分取平均。支持各去掉 1–5 个最高和最低评委总分后求平均，不逐项去极值；相同分数也只删除指定份数。计算使用十进制数，最终四舍五入保留两位小数。人数不足时不生成最终分或名次、不允许公布；提名保留全部有效评委的意见。成绩页和 CSV 显示规则、采用评分数及去极值份数。

开始保存任何评分（包括草稿）或公布成绩后，算分规则锁定；事前可一键恢复默认规则。修改规则会使旧评分表失效，需重新打开核对。停用、标为垃圾账户、移除角色和队伍成员自己的评分不进入统计。每位评委每个特别奖最多确认提名 3 项；系统自动排除本人所属队伍。非本人队伍的其他利益冲突需主办方事先调整评委安排。统计显示已评/应评数量，缺评作品不进入正式排名，同分并列。成绩默认私有；全部有效评委完成后才能公布。公布后关闭评分变更，选手能看到改进建议。

### 内容与发布

公告、教程与指南、日程、赛道四类内容各有草稿、已发布、已归档三种状态，新建时默认草稿。编辑页把「保存草稿」「发布 / 更新公开版」「归档」做成三个独立按钮，点哪个按钮就按哪种状态落库；新内容默认停在草稿，不点发布绝不会接触选手端，而对已发布条目点「保存草稿」会当场把它从选手端下架，页面会先要求确认。请求里没有按钮标识或标识不认识时，本次不保存任何内容并在页面说明。选手端的公告列表、日程与小时历、教程与指南列表、必读检查和各类直达页面只读取已发布条目，草稿与归档条目直接访问其公开地址返回 404；「发布 / 更新公开版」会用当前内容覆盖此前的公开版并记录最后发布时间。归档只停止公开，记录与引用都保留，队伍仍显示它当初选择的赛道，操作日志按内容类别分别记录存草稿、发布和归档。升级前已存在的公告、教程、日程与赛道由迁移 `0015_content_publish_state` 统一标为已发布，已有活动不会因此变空。加分规则不套用这套生命周期，仍由自身的「公布并接受申请」开关控制。

赛道以外的公告、教程与日程在编辑页提供预览，用选手端的真实模板渲染这一条并隐藏主办方编辑入口，页首注明这条当前的发布状态。预览只读：不修改状态、不发布、不记录阅读进度、不写操作日志，且只对主办方开放，选手与志愿者访问返回 403。

四个发布开关（活动公开、作品展厅、评委打分、成绩公布）已移出“活动设置”表单，只在“发布准备”页面（`/hackathon/tongzhou26/manage/publish/`）以各自的按钮逐个提交；设置页不再包含这些字段，普通设置编辑无论提交什么都不会改动开关。开启前逐项检查前置条件：公开活动需要至少一个已发布赛道和合法的起止时间，开放评分需要至少一位可用评委（账户已停用或标为垃圾的不计入）与已通过审核的作品，开放展厅需要同意公开且已通过审核的作品，公布成绩需要全部有效评分收齐。条件不满足时开关保持原样并列出全部原因；关闭任一开关永不被拦截。每次生效的开启和关闭都写入操作日志。

“发布准备”下方是七行发布前清单：基本信息、时间与截止、赛道、必读材料、评委名单、成绩完整性、内容草稿。每行给出当前结论和一个“去处理”链接，时间与截止、成绩完整性还会列出具体不合规的条目。活动起止时间改动后，清单与“活动设置”页面同时提示不再一致的截止项与日程项（例如某项晚于活动结束时间、某条日程落在新区间之外），并分别链接到活动设置或该条日程的编辑页；平台只提醒，不自动移动任何日期。

## 现场本地播放助手

浏览器不能直接控制现场电脑的原生 PPT 进程，因此提供独立助手 `eventyay.hackathon.companion`。助手使用 Python 标准库，文稿播放需要现场安装 LibreOffice。它只控制自己启动的独立 LibreOffice 实例，不关闭其他办公进程。

1. 在路演调度生成 12 小时令牌。令牌只显示一次，数据库只保存哈希；生成新令牌会撤销旧令牌，也可主动撤销。角色权限和令牌过期均由服务器检查。
2. 在现场电脑执行，按提示粘贴令牌；不要把令牌放进 URL 或共享文档：

```bash
python -m eventyay.hackathon.companion \
  --url https://your-site.example/hackathon/tongzhou26/station/state/ \
  --cache ./stage-cache
```

3. 默认只进行演练与材料缓存。确认现场播放效果后添加 `--execute`；可用 `--office /path/to/soffice` 指定 LibreOffice。使用 `--unpack` 可安全解压 ZIP 附件，助手不会执行附件中的脚本。
4. 在无队伍展示时预下载队列材料，校验大小和 SHA-256，避免现场临时下载。开始展示时打开该队文稿，展示到点自动结束由助手启动的进程；结束本队或关闭助手也会清理该进程。暂停状态不会继续消耗展示时间。
5. 主办方另开路演大屏展示倒计时。网页 Demo 与备用录屏由现场技术人员使用缓存或链接切换；当前助手不自动登录网站、不启动项目源码、不保证不同办公软件的排版一致。

助手拒绝携带令牌跟随重定向或访问其他域；非本机地址要求 HTTPS。本地 HTTP 仅允许回环地址。断线保留到点结束保障，持续失联时关闭自己启动的播放进程。请提前验证专用电脑、视频声音、翻页笔、转接头、网络与备用方案；这里没有自动化的校内算力供应或远程桌面控制。

## 截止前排队提交与凭证

大文件上传先登记一个小请求，再在浏览器计算 SHA-256 并绑定到该上传任务，最后按 8 MiB 分片传输。凭证记录服务器登记时间、本机点击时间、文件名、大小、哈希与哈希绑定时间，可在「我的作品」查询并下载带服务器签名的 JSON。只有服务器已确认的登记才允许续传；本机时间不能用来绕过截止。若哈希在截止后才绑定，凭证只能证明截止前登记了文件信息，不能证明该内容在截止前已固定。

截止前登记的任务可持续至登记后 24 小时或活动的材料最终冻结时间，以较早者为准。续传不会延长此期限；截止后不能创建新任务。已经开始路演或确认评分的作品仍不能替换材料。

每个活动默认开放 4 个上传通道（`constants.py` 的 `UPLOAD_SLOTS`），通过数据库中的 120 秒租约在多个 Web worker 间共享限制。浏览器先请求通道再发送分片，服务端分片与完成接口也再次检查通道。无通道或磁盘不足时返回 429 和 `Retry-After`，前端使用有随机抖动的退避重试。离线或暂停后租约会自动释放；此机制不承诺严格先来先服务或准确等待时间。反向代理仍需限制请求大小并保留请求缓冲，否则慢速请求可能在到达应用前占用连接。单机上多个活动的总容量需要另行控制。

「正式提交 / 排队登记」允许将尚在上传的材料纳入提交清单。登记会锁定作品文字与已有上传任务清单，记录清单哈希和服务器时间；所需材料全部校验通过后自动正式提交。其他必填项仍必须齐全。取消上传、上传过期或校验失败不会成为成功提交。可取消排队提交后编辑，但截止后不能重新登记正式提交或更换文件。关闭页面不会在后台继续上传，需要保持页面打开或重新选择同一文件续传。

`cleanup_hackathon_uploads` 继续清理过期临时文件，但不再按七天删除上传记录；凭证随活动保留，便于后续技术核查。部署此次改动需运行 `python manage.py migrate hackathon`。

## ZIP 一级目录预览

已保存的 ZIP 附件提供一级目录预览。服务端仅读取有界的 ZIP 目录索引，不解压到磁盘、不执行内容，也不读取压缩文件正文。沿用上传的目录大小与条目数限制（目录不超过 4 MiB、最多 20000 个条目），最多返回 200 个一级条目，聚合子目录的文件数量和声明大小。仅队友、评委和主办方有权限查看；其他活动和未授权用户不能访问。文件名以文本显示，目录预览不证明压缩内容可运行或全部可解压。RAR / 7z 不在目前支持范围内。
