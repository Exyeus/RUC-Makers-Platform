# 上届材料的匿名元数据统计

统计日期：2026-10-25。用途：为本届提交平台确定材料类型、上传容量、归档处理和留存需求。统计仅涉及本地文件与归档目录项，不使用参赛作品正文。

## 结论与统计分母

现有资料包含 **34 个非空收集单元**，另有 3 个空目录。递归找到 32 个归档文件；其中 6 个位于工程或展开目录内部，另有 1 个浅层归档本身已包含在一个外层整理包中。按可核验的包含关系消除边界重复后，保留 **25 个浅层归档候选**，涉及 **23 个收集单元**。另外 11 个非空单元只剩散件，未保留可识别的浅层原包。

**无法可靠给出独立参赛提交数或队伍数的上下界。** 归档可能是附件包、工程内部包或后来整理的包；同一原始提交可能包含多个包，外层上传记录也不完整。25 是归档边界候选数，34 是非空收集记录数，均不等于已确认的独立提交数；不能把目录编号直接换算成队伍数。

本文提供两组出现率：以 **34 个非空收集单元**作提交记录的代理分母，每单元同一类型只记一次；以 **25 个归档候选**作保存包的分母。前者覆盖散件，后者适合评估包的结构，两列不能混为同一批原始上传的完整统计。解压副本和包内嵌套归档不增加分母。

## 方法与边界

- Windows PowerShell 只读取文件系统元数据；Ubuntu/WSL 使用 Python 标准库和 7-Zip 读取归档目录项、大小与 CRC，并计算现存归档的 SHA-256。
- ZIP 读取中央目录，RAR/GZ 仅列目录；不运行参赛代码，不打开作品正文、图片、视频或链接，不新建解压目录，不修改或删除源资料。
- 先用归档 SHA-256 判断字节级重复，再比较成员大小/CRC 全集。以同一收集单元内的文件大小/CRC 匹配识别已有展开内容；根层整理包允许跨单元查找。大小/CRC 匹配是内容对应证据，存在 CRC 碰撞的理论可能，也不证明原始上传身份或完整路径结构。
- 类型依据扩展名和标准工程清单文件名，不判断作品内容、质量、版权归属或可运行性；已识别的依赖、构建、版本控制、系统附属和工具目录不用于主材料类型判定。嵌套归档未递归重解压，归档内部的 Office 文档也不当作通用 ZIP 再展开统计。
- 详细路径、原文件名、逐文件指纹及匹配关系仅保存在本地私有清单；本报告与聚合 JSON 不包含姓名、项目名、联系方式、原文件名、原路径、原件、源码片段或媒体内容。匿名统计不代表取得作品使用授权。

## 对新平台的建议（待确认）

以下是由资料样本推导的建议，供需求确认和分期取舍；不代表本届已定范围、容量上限或当前实现已通过验证。首版优先把材料用途、上传记录、状态、访问范围和授权说明传递清楚，自动展开与深层索引可按实际需要后置。

1. **上传记录与逻辑提交分开建模。** 保存上传记录 ID、逻辑提交 ID、版本、上传时间、原包字节数、哈希和处理状态；单次提交可有多附件，内嵌包与展开副本不新增逻辑提交。目录编号和文件名不作为身份依据。
2. **表单明确材料角色。** 图像、演示文稿、视频、源码/工程包、链接和可运行附件分别声明；文件探测只辅助校验，不用扩展名替代选手填写的材料用途。
3. **容量按整包和展开量分别限制。** 本样本最大候选为 228.17 MiB、声明展开量最大 372.63 MiB、最大文件数 1,489；若希望覆盖这些现存候选，上传、代理、对象存储、后台超时和处理配额至少都要覆盖这些量级，并保留明确余量。这些值不是本届最终上限，也不代表未保留原包的 11 个单元的完整上传大小。
4. **使用后台流式处理与清晰状态。** 支持进度、失败重试、校验后确认和幂等上传；归档检查与元数据索引异步完成，避免千文件工程或百 MiB 文件阻塞页面请求。预检包括路径归一化、编码、展开字节数/文件数、层数及嵌套包，不自动运行项目。
5. **保留原包作为证据，展开件独立标识。** 原包、派生索引和临时展开件分开留存；用哈希识别同一原件，用逻辑提交与版本关联多份包。工程附属目录可提示选手自查，但不能据本统计擅自删除原材料。
6. **把材料访问与作品使用授权分开。** 原件默认仅授权评审/工作人员访问；公开项目卡、作品图片、演示视频、源码、案例展示和训练用途分别取得明确授权，并留存版本与撤回渠道。匿名汇总可以帮助设计平台，不能替代授权。
